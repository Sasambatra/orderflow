# Материалы для портфолио

## Описание проекта

**OrderFlow — backend обработки заказов и резервирования остатков.**
Сервис предотвращает перепродажу ограниченного товара, безопасно обрабатывает повторы
HTTP-запросов и платежных событий, восстанавливает фоновые уведомления через transactional outbox.
Стек: Python, FastAPI, PostgreSQL, SQLAlchemy, Alembic, Redis, Celery, Docker, pytest.

## Формулировка для резюме

> **OrderFlow — Python backend для заказов и складских резервов.** Реализовал атомарное
> резервирование с блокировками PostgreSQL, идемпотентные операции и обработку HMAC webhook
> тестового платёжного провайдера. Добавил transactional outbox, Celery, отзывные JWT-сессии,
> ролевой доступ, миграции и автоматические тесты конкурентных сценариев.

## Что показать за 5–7 минут

1. Открыть Swagger и диаграмму из architecture.ru.md. Объяснить состояния заказа и правило остатков.
2. Выполнить `make demo`: заказ → повтор того же запроса → mock payment → webhook → paid → inbox.
3. Выполнить `make benchmark`: 20 одновременных покупателей, одна единица, один 201 и 19 бизнес-конфликтов.
4. Показать тест `test_twenty_retries_one_order`: все 20 повторов возвращают один заказ.
5. Показать e2e `test_redis_outage_preserves_order_and_recovers_inbox`: отдельный Redis останавливается, заказ сохраняется, после перезапуска появляется одно уведомление.
6. Объяснить позднюю оплату через тест `test_late_payment_requires_refund` и admin refund_required.
7. Открыть проверенные результаты, workflow CI и ограничения версии.

Не показывайте `.env`, пароли, Authorization и реальные учётные данные в записи демонстрации.

## Вопросы для собеседования

**Почему недостаточно просто проверить stock перед INSERT?**
Два параллельных запроса могут прочитать один остаток. Блокировка и изменение счётчика
в общей транзакции сериализуют решение; CHECK-ограничения дополнительно защищают допустимое состояние.

**Почему хранится результат запроса, а не только UUID заказа?**
Клиент может не получить ответ после commit. Повтор должен вернуть тот же status/body,
а изменение payload с прежним ключом должно быть обнаружено.

**Почему очередь не является источником истины?**
Запись в PostgreSQL и publish в Redis не входят в одну транзакцию.
Outbox фиксируется с заказом и остаётся доступным до завершения consumer.

**Где гарантия однократного эффекта?**
HTTP/webhook используют уникальные ключи. В consumer вставка локального inbox и processed_at
атомарны. Для сторонней почты или банковского API понадобятся дополнительные гарантии провайдера.

**Почему поздний success не выбрасывается?**
Деньги могли поступить у провайдера после освобождения резерва. Событие сохраняется как
refund_required для разбора, без повторного расходования товара.

**Что улучшить дальше?**
Реальная интеграция оплаты и возврата, email verification/recovery, правила хранения
персональных данных, метрики нескольких экземпляров, нагрузка в целевой среде и операционные SLO.
